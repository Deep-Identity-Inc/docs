title: Submit Workflow Step
description: Submit and execute one step of a workflow session
api: POST /v1/sessions/{session_id}/steps/{step_id}
---

```
POST /v1/sessions/{session_id}/steps/{step_id}
```

Submits the data for one workflow step and executes it synchronously. The request body's shape is **config-driven** — it depends on both `step_id` and the settings configured on that step within the workflow — see [Step submission schemas](#step-submission-schemas) below.

Steps must be submitted **in order**: the `step_id` in the URL must match the session's `current_step` (as returned by [Create Workflow Session](/api-reference/workflow-runner/create-workflow-session) or [Get Workflow State](/api-reference/workflow-runner/get-workflow-state)), and that step must be `PENDING` or `IN_PROGRESS`.

## Request

### Headers

| Header | Required | Description |
|---|---|---|
| `x-api-key` | Yes | Your organization's API key |

### Path parameters

| Parameter | Type | Required | Description |
|---|---|---|---|
| `session_id` | string (uuid) | Yes | The session to submit a step for |
| `step_id` | string | Yes | One of the [runnable steps](/api-reference/workflow-runner/create-workflow-session#available-steps), e.g. `ID_VERIFICATION` — must match the session's current step. Case- and separator-insensitive: `id_verification` and `id-verification` also work |

### Body parameters

The request body depends on `step_id`:

| `step_id` | Body schema |
|---|---|
| `ID_VERIFICATION` | [ID_VERIFICATION submission](#id_verification) |
| `FACE_LIVENESS` | [FACE_LIVENESS submission](#face_liveness) |
| `PHONE_VERIFICATION` | [PHONE_VERIFICATION submission](#phone_verification) |
| `IP_JURISDICTION`, `VPN_DETECTION`, `INJECTION_DETECTION`, `ANTI_CHEAT` | [iGaming step submissions](#igaming-steps) |

## Step submission schemas

### ID_VERIFICATION

<Info>
  Get `uploads` values from [Create Session Uploads](/api-reference/workflow-runner/create-session-uploads) — upload each image to its presigned URL first, then submit the returned `file_key` values here.
</Info>

| Field | Type | Required | Description |
|---|---|---|---|
| `document_type` | string | Yes | The type of the primary document being submitted, e.g. `passport-us` |
| `secondary_document_type` | string | Only if the step requires a secondary ID | Type of the secondary document |
| `tertiary_document_type` | string | Only if the step requires a tertiary ID | Type of the tertiary document |
| `uploads.id_front` | string | Yes | File key for the primary document's front image |
| `uploads.id_back` | string | Yes, unless `document_type` is a front-only type (see `front_only_document_types` in [requirements](/api-reference/workflow-runner/create-workflow-session#id_verification-requirements)) | File key for the primary document's back image. Rejected if supplied for a front-only document type |
| `uploads.secondary_id_front` | string | Only if a secondary ID is required | File key for the secondary document's front image |
| `uploads.secondary_id_back` | string | Same front/back rule as `id_back`, keyed off `secondary_document_type` | File key for the secondary document's back image |
| `uploads.tertiary_id_front` | string | Only if a tertiary ID is required | File key for the tertiary document's front image |
| `uploads.tertiary_id_back` | string | Same front/back rule as `id_back`, keyed off `tertiary_document_type` | File key for the tertiary document's back image |
| `uploads.selfie_front` | string | Yes | File key for the selfie image |

Which of these fields are required or accepted for a given session depends on that step's configuration (whether it requires a secondary/tertiary ID), not on this table alone — check the step's `requirements` from [Create Workflow Session](/api-reference/workflow-runner/create-workflow-session#id_verification-requirements) or [Get Workflow State](/api-reference/workflow-runner/get-workflow-state).

### FACE_LIVENESS

The body is a discriminated union on `action`. All variants also accept `frame_count` and `clip_mime_type`, but those are only meaningful — and only validated — when `action` is `upload-url`.

| `action` | Fields | Description |
|---|---|---|
| `start` | none | Mints a Rekognition Face Liveness session and returns streaming credentials for the client SDK |
| `complete` | none | Fetches the liveness result server-side once the client has finished streaming |
| `upload-url` | `frame_count` (integer, 1-8, required), `clip_mime_type` (string, optional) | Custom liveness provider only — mints upload URLs for captured frames/clip. Not used with the default provider |

```bash cURL — start
  -H "Content-Type: application/json" \
  -d '{ "action": "start" }'
```

  With the custom liveness provider, call `upload-url` and upload the captured frames before you call `complete`. Calling `complete` before any frame is uploaded returns `409` with `code` `LIVENESS_UPLOAD_INCOMPLETE`. No attempt is used: upload the frames and call `complete` again.
</Note>

### PHONE_VERIFICATION

The phone verification step calls the applicant's phone on file and checks the phrase they speak. The body is a discriminated union on `action`, and no other fields are accepted.

| `action` | Fields | Description |
|---|---|---|
| `start` | none | Places the verification call. If a call for this step is already in progress, it's reused (`phone_verification.reused: true`) instead of placing a second one |
| `complete` | none | Reads the call's result and applies it to the step |

The step is asynchronous: its `requirements` include `asynchronous: true` and `poll_interval_seconds: 5`. After `start`, call `complete` every 5 seconds until the step settles.

| What happens | Response | Attempt used |
|---|---|---|
| The call is still in progress | `409`, `code` `STEP_NOT_READY`. Keep polling `complete` | No |
| The applicant spoke the right phrase | `200`, step `COMPLETED`, `phone_verification.passed: true` | No |
| The applicant spoke the wrong phrase | `200`, step `PENDING`, `failure.code` `PHONE_VERIFICATION_FAILED` | Yes |
| The call wasn't answered, went to voicemail, or didn't connect | `200`, step `PENDING`, `failure.code` `PHONE_CALL_FAILED` | Yes |
| You call `complete` again after a failed call | `409`, `code` `STEP_NOT_READY`, `failure_reason` `PHONE_VERIFICATION_NOT_STARTED`, `error` "Start a new phone verification call to try again" | No |
| The phone verification service times out or is unavailable on `start` | `503`, `code` `PHONE_VERIFICATION_UNAVAILABLE`, `error` "The phone verification service is temporarily unavailable; try again". The step is unchanged | No |
| The applicant has no valid phone on file on `start` | `400`, `code` `PHONE_REQUIRED` | No |

Both failed outcomes are retryable while the session has attempts left: call `start` to place a new call, then poll `complete` again. Each call counts as at most one failed attempt. After a `503`, retry the same `start` call.

To avoid `PHONE_REQUIRED`, send the applicant's `phone` when you create the session. See [Create Workflow Session](/api-reference/workflow-runner/create-workflow-session#phone-number).

<CodeGroup>

```bash cURL — start
curl -X POST https://api.deepidv.com/v1/sessions/80e801af-991b-425c-96fc-f5e07d794253/steps/PHONE_VERIFICATION \
  -H "x-api-key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "action": "start" }'
```

```bash cURL — complete

```

### iGaming steps

The four iGaming checks can run as workflow steps through the runner, with the same inputs and verdicts as their [standalone endpoints](/api-reference/igaming/overview). The session's `steps[].requirements` (from [Create Workflow Session](/api-reference/workflow-runner/create-workflow-session)) lists the fields each one needs.

| `step_id` | Body | Result field in the response |
|---|---|---|
| `IP_JURISDICTION` | `{ "ip_address": "<applicant IPv4 or IPv6>" }` | `ip_jurisdiction` — same fields as [IP jurisdiction](/api-reference/igaming/ip-jurisdiction), with snake_case keys |
| `VPN_DETECTION` | `{ "ip_address": "<applicant IPv4 or IPv6>" }` | `vpn_detection` — same fields as [VPN detection](/api-reference/igaming/vpn-detection), with snake_case keys |
| `INJECTION_DETECTION` | `{ "device_integrity": {...}, "media_source": {...}, "frame_timing": {...} }` (each `{ pass, score, signals }`) | `injection_detection` — same fields as [Injection detection](/api-reference/igaming/injection), with snake_case keys |
| `ANTI_CHEAT` | `{ "image": "<base64 JPEG/PNG>", "device_fingerprint": "<optional>" }` | `anti_cheat` — same fields as [Anti-cheat](/api-reference/igaming/anti-cheat), with snake_case keys |

The standalone endpoints return some evidence keys in camelCase. Through the runner, every key in these result objects is snake_case.

A `block` action fails the step and the session. Submit the steps one at a time, in the session's step order.

```bash
curl -X POST https://api.deepidv.com/v1/sessions/80e801af-991b-425c-96fc-f5e07d794253/steps/IP_JURISDICTION \
  -H "x-api-key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "ip_address": "102.88.25.10" }'
```

## Response

The response is a common envelope for every step type. FACE_LIVENESS additionally includes a `liveness` object, PHONE_VERIFICATION a `phone_verification` object, and each iGaming step its result field (see [iGaming steps](#igaming-steps)).

<Note>
  Every key in the response, including step result objects, is snake_case. The one exception is `liveness.script` on the custom-provider FACE_LIVENESS `start` response, which keeps its camelCase keys (`challengeType`, `durationMs`, `steps[].atMs`). See [FACE_LIVENESS results](#face_liveness-results).
</Note>

### 200 — Success

| Field | Type | Present when | Description |
|---|---|---|---|
| `step_id` | string | always | The submitted step id |
| `step_status` | string | always | `PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED`, or `SKIPPED` |
| `failure_reason` | string \| null | always | Legacy reason the step failed this attempt, or `null`. Kept for existing integrations and no longer extended: use `failure.code` instead |
| `failure` | object \| null | always | Why this attempt failed a blocking check, whether the step can be retried (`step_status: PENDING`) or not (`FAILED`). `null` on success and on intermediate transitions such as liveness `start`. See [Failure codes](/api-reference/workflow-runner/get-workflow-state#failure-codes) |
| `session_failure` | object \| null | always | Why the run ended, when this submission failed the session. `null` otherwise. See [Session failure codes](/api-reference/workflow-runner/get-workflow-state#session-failure-codes) |
| `current_step` | integer \| null | always | 0-based index of the next step to submit. `null` once the run has finished |
| `attempts_remaining` | integer \| null | always | Session-wide failure budget remaining. `null` when the workflow has no failure limit configured |
| `session_status` | string | always | Session status: `PENDING`, `SUBMITTED`, `VERIFIED`, `REJECTED`, `VOIDED`, `EXPIRED`, or `FAILED` |
| `session_progress` | string | always | `PENDING`, `STARTED`, or `COMPLETED` |
| `liveness` | object | `step_id` is `FACE_LIVENESS` | Shape depends on the submitted `action` — see [FACE_LIVENESS results](#face_liveness-results) |
| `phone_verification.status` | string | `step_id` is `PHONE_VERIFICATION` | Call state, such as `pending`, `in-progress`, or `completed` |
| `phone_verification.reused` | boolean | `start` | `true` when an existing in-progress call was reused instead of placing a new one |
| `phone_verification.passed` | boolean | `complete` | `true` when the applicant spoke the right phrase |

<Note>
  Advisory checks (age, expiry, document validity period, state) never fail an `ID_VERIFICATION` step and are not included in the response — only the blocking checks below can produce a `failure_reason`.
</Note>

### ID_VERIFICATION failure reasons

These are the legacy `failure_reason` values. For new integrations, read `failure.code` instead. See [Failure codes](/api-reference/workflow-runner/get-workflow-state#failure-codes).

| `failure_reason` | Meaning |
|---|---|
| `FACE_NOT_DETECTED_IN_ID` | No face was detected on the primary document's front image |
| `OCR_NAME_MISSING` | No first/last/middle name could be extracted from the document |
| `ID_CLASSIFICATION_FAILED` | The document's detected type doesn't match, or isn't an accepted, document type |
| `ID_TYPE_UNRECOGNIZED` | The document's type field couldn't be read |
| `ID_TYPE_LOW_CONFIDENCE` | The document's type field was read with too little confidence |
| `DOC_TYPE_NOT_ALLOWED` | The detected document type doesn't match the declared `document_type` family |
| `NO_FACE_DETECTED` | No face was detected in the selfie image |
| `FACE_MISMATCH` | The selfie face doesn't match the document's face closely enough |
| `LIVENESS_ID_MISMATCH` | The face captured during the `FACE_LIVENESS` step doesn't match the document's face |

### FACE_LIVENESS results

`liveness` depends on the submitted `action`:

**`start`**

| Field | Type | Description |
|---|---|---|
| `liveness_session_id` | string | The Rekognition Face Liveness session ID the client streams to |
| `region` | string | AWS region for the liveness session, e.g. `us-east-1` |
| `credentials.access_key_id` | string | Temporary AWS access key |
| `credentials.secret_access_key` | string | Temporary AWS secret key |
| `credentials.session_token` | string | Temporary AWS session token |
| `credentials.expiration` | string | ISO 8601 expiry of the credentials (~15 minutes) |
| `expires_at` | string | ISO 8601 expiry of the liveness session |

With the custom liveness provider, `start` returns `liveness_session_id` and a `script` the capture must follow, instead of `region` and `credentials`. `script` keeps camelCase keys:

| Field | Type | Description |
|---|---|---|
| `script.challengeType` | string | `FaceMovementChallenge` or `FaceMovementAndLightChallenge` |
| `script.durationMs` | number | Length of the challenge in milliseconds |
| `script.steps[].kind` | string | `color` or `move-closer` |
| `script.steps[].atMs` | number | When the step starts, in milliseconds from the start of the challenge |
| `script.steps[].color` | string | Hex color to show, for `color` steps |

**`complete`**

| Field | Type | Description |
|---|---|---|
| `status` | string | Outcome of this attempt: `SUCCEEDED` when the step passed, `FAILED` for any failed attempt (the liveness check failed, or the liveness face didn't match the ID) |
| `confidence` | number | Liveness confidence score (0-100). Present only on a pass. It's left out of a failed attempt on purpose, so the score can't be used to tune a spoof against the threshold |
| `passed` | boolean | `true` when `status` is `SUCCEEDED` and `confidence` meets the step's configured threshold |

### FACE_LIVENESS failure reasons

| `failure_reason` | Meaning |
|---|---|
| `FACE_LIVENESS_CHECK_FAILED` | The liveness check completed but did not pass (`passed: false`). Returned in a `200` response, not an error. `failure.code` is `LIVENESS_FAILED` |

<Note>
  Calling `complete` before `start`, before Rekognition has finished processing, or (custom provider) before any frame is uploaded returns a `409` with `code` `LIVENESS_NOT_STARTED`, `LIVENESS_RESULT_NOT_READY`, or `LIVENESS_UPLOAD_INCOMPLETE` — see [Error responses](#error-responses). These are retryable and don't consume an attempt.
</Note>

### Error responses

Error bodies carry an `error` message and a machine-readable `code`; handle `code` values you don't recognize. Authentication failures rejected before the request reaches the runner may have no `code`. Retryable `409` responses also carry a legacy `failure_reason`.

| Status | Description |
|---|---|
| `400` | Invalid `session_id`/`step_id` path parameters, the request body fails the step's schema, an upload key in the body doesn't belong to this session, or a step that uses the applicant's phone (PHONE_VERIFICATION `start`, PHONE_TRUST_CHECK, CARRIER_AGE_GATE, PHONE_OWNERSHIP_MATCH) runs on a session whose applicant has no phone on file (`PHONE_REQUIRED`) |
| `401` | Invalid or missing API key |
| `403` | The session belongs to a different organization |
| `404` | Session not found, `step_id` isn't one of the [runnable steps](/api-reference/workflow-runner/create-workflow-session#available-steps), the step isn't part of this session's workflow, or no workflow execution state exists for this session |
| `409` | The session is terminal (`SESSION_TERMINAL`), the step is out of order (`STEP_OUT_OF_ORDER`) or not in a submittable state (`STEP_NOT_SUBMITTABLE`), a concurrent submission conflict occurred (`STEP_CONFLICT`), liveness `complete` came before `start`, before the result was ready, or before any upload (`LIVENESS_NOT_STARTED`, `LIVENESS_RESULT_NOT_READY`, `LIVENESS_UPLOAD_INCOMPLETE`), or another step is waiting on state that doesn't exist yet (`STEP_NOT_READY`, for example a phone call still in progress). The not-ready conflicts are retryable and don't use an attempt |
| `429` | Too many requests |
| `501` | This step type isn't runnable through the API yet |
| `503` | PHONE_VERIFICATION `start` couldn't reach the phone verification service (`PHONE_VERIFICATION_UNAVAILABLE`). Retryable: the step is unchanged and no attempt is used |
