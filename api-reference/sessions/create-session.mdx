```
POST /v1/sessions
```

Creates a new identity verification session and optionally sends email and SMS invitations to the applicant.

## Request

### Headers

| Header         | Required | Description        |
| -------------- | -------- | ------------------ |
| `x-api-key`    | Yes      | Your API key       |
| `Content-Type` | Yes      | `application/json` |

### Body parameters

Both camelCase and snake_case parameter names are accepted. If both are provided for the same field, the camelCase value takes priority.

| Parameter           | Alias             | Type    | Required | Description                                                                                          |
| ------------------- | ----------------- | ------- | -------- | ---------------------------------------------------------------------------------------------------- |
| `first_name`        | `firstName`       | string  | No       | Applicant's first name. Optional, see [Applicant names](#applicant-names)                                                                             |
| `last_name`         | `lastName`        | string  | No       | Applicant's last name. Optional, see [Applicant names](#applicant-names)                                                                                |
| `email`             | —                 | string  | Yes      | Applicant's email address                                                                            |
| `phone`             | —                 | string  | No       | Applicant's phone number in E.164 format (e.g. `+15192223333`). Required when the workflow has a step that uses the applicant's phone and the applicant has no valid phone on file. See [Phone number](#phone-number) |
| `external_id`       | `externalId`      | string  | No       | Your internal reference ID for this session                                                          |
| `send_email_invite` | `sendEmailInvite` | boolean | No       | Send an email invitation to the applicant. Defaults to `true`                                        |
| `send_phone_invite` | `sendPhoneInvite` | boolean | No       | Send an SMS invitation to the applicant. Defaults to `true`. Skipped if the applicant has no phone on file |
| `workflow_id`       | `workflowId`      | string  | No       | ID of the workflow to use. If omitted, runs as a standalone verification                             |
| `redirect_url`      | `redirectUrl`     | string  | No       | HTTPS URL to redirect the end-user to after the verification session ends. Must be a valid HTTPS URL |
| `expires_in_hours`  | `expiresInHours`  | integer | No       | Auto-expire the session after this many hours (1-8760). Overrides the workflow's expiry setting if both are provided. If omitted, the workflow's expiry setting is used (if configured) |

### Applicant names

`first_name` and `last_name` are optional. Sending only one of them is fine, for applicants with a single name.

If you send neither (or both are blank), the session is created without names:

- The session and its webhooks carry `names_provided: false`.
- The names are read from the applicant's ID document, and the name-matches-ID check is skipped.
- The workflow must include an ID verification step. It can't include a step that matches on the name (`DEEP_AGE`, `CREDIT_CHECK`, `PHONE_OWNERSHIP_MATCH` or an identity-number lookup), and it can't have an `E_SIGNATURE`, `PEP_SANCTIONS`, `BACKGROUND_CHECK` or `ADDRESS_VERIFICATION` step before the ID verification step.

Otherwise the create returns `400` with `code` `NAMES_REQUIRED_NO_ID_STEP` (the workflow has no ID verification step) or `NAMES_REQUIRED_FOR_STEP` (with `steps` listing the steps that need the name).

### Phone number

A workflow with a step that uses the applicant's phone (`PHONE_VERIFICATION`, `PHONE_TRUST_CHECK`, `CARRIER_AGE_GATE`, or `PHONE_OWNERSHIP_MATCH`) needs a valid phone for the applicant. Otherwise `phone` is optional.

- A phone counts as on file only if it's a valid E.164 number.
- If the applicant already has a valid phone on file, that phone is kept, even if you send a different one.
- If the applicant's phone on file is missing or invalid, the `phone` you send fills it.
- If there's no valid phone on file and you don't send one, the create returns `400` with `code` `PHONE_REQUIRED` and `steps` listing the steps that need the phone.

A ProofCall step doesn't need the applicant's phone: it calls the references sent with its own submission.

## Response

### 200 — Success

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Unique identifier for the created session |
| `session_url` | string | URL where the applicant completes verification. Workflow sessions use `/session/<id>`; sessions created without a `workflow_id` use `/verification/<id>` |
| `externalId` | string | Your external ID (only returned if provided in the request) |
| `expires_at` | string | ISO 8601 timestamp when the session will auto-expire. Only present when the session has an expiry (`expires_in_hours`, or the workflow's session expiry setting). If it's absent, the link doesn't expire |
| `links` | array | Associated verification links |

### Error responses

| Status                  | Description                                                   |
| ----------------------- | ------------------------------------------------------------- |
| `400 Bad Request`       | Invalid request body — check required fields and, if provided, phone format. Also returned with `code` `PHONE_REQUIRED` (and `steps`) when the workflow needs the applicant's phone and none was sent or is on file, and with `code` `NAMES_REQUIRED_NO_ID_STEP` or `NAMES_REQUIRED_FOR_STEP` when no names were sent but the workflow needs them (see [Applicant names](#applicant-names)) |
| `401 Unauthorized`      | Missing or invalid API key                                    |
| `402 Payment Required`  | Insufficient token balance                                    |
| `404 Not Found`         | Workflow ID not found                                         |
| `429 Too Many Requests` | Rate limit exceeded                                           |

## Redirect URL

When a `redirect_url` is provided in the request, the returned `session_url` will include it as an encoded query parameter:

```
https://verify.deepidv.com/session/<session_id>?oid=<org_id>&redirect_url=https%3A%2F%2Fyourapp.com%2Fverify-callback
```

Upon session completion, failure, or user exit, the verification app will redirect the end-user back to your `redirect_url` with the following query parameters appended:

| Parameter    | Type   | Description                                                           |
| ------------ | ------ | --------------------------------------------------------------------- |
| `session_id` | string | The session ID                                                        |
| `status`     | string | The outcome of the session                                            |
| `reason`     | string | Additional context for the outcome (omitted when status is `success`) |

### Status values

| Value       | Description                                                   |
| ----------- | ------------------------------------------------------------- |
| `success`   | Verification session was completed and submitted successfully |
| `failed`    | Session encountered an error during the verification process  |
| `abandoned` | User manually exited the session without completing           |
| `expired`   | Session was automatically expired before the user completed verification |

### Reason values

| Value                 | Description                                                                           |
| --------------------- | ------------------------------------------------------------------------------------- |
| `document_unreadable` | The uploaded ID document could not be processed (blurry, glare, wrong doc type, etc.) |
| `face_mismatch`       | Liveness/selfie did not match the document photo                                      |
| `session_expired`     | The session timed out before the user completed verification                          |
| `internal_error`      | An unexpected server-side error occurred                                              |
| `user_cancelled`      | User explicitly chose to leave/cancel the verification                                |
| `unknown`             | Catch-all for any unclassified failure                                                |

<Info>
  The `reason` parameter is omitted when `status=success`. When
  `status=abandoned`, the reason will typically be `user_cancelled`. New reason
  values may be added in the future — your integration should handle unknown
  reasons gracefully.
</Info>

### Example redirect URLs

```bash
# Success
https://yourapp.com/verify-callback?session_id=sess_abc&status=success

# Failure
https://yourapp.com/verify-callback?session_id=sess_abc&status=failed&reason=document_unreadable

# Abandoned
https://yourapp.com/verify-callback?session_id=sess_abc&status=abandoned&reason=user_cancelled

# Expired
https://yourapp.com/verify-callback?session_id=sess_abc&status=expired&reason=session_expired
```
