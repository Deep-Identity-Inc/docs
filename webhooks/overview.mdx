Webhooks allow you to receive real-time notifications when events happen in your deepidv account. Instead of polling the API, deepidv pushes event data to your application's webhook endpoint as a JSON payload via HTTP POST.

Receiving webhook events helps you respond to asynchronous events, such as when a verification session is submitted, verified, or rejected.

## Get started

To start receiving webhook events in your app:

<Steps>
  <Step title="Create a webhook endpoint">
    Set up an HTTPS endpoint on your server to receive POST requests from deepidv.
  </Step>
  <Step title="Register your endpoint">
    Add your webhook endpoint URL in the deepidv Admin Console under **Integrations > Webhooks**.
  </Step>
  <Step title="Select events">
    Choose which event types you want to subscribe to.
  </Step>
  <Step title="Verify signatures">
    [Verify each incoming request](#verifying-webhooks) using your signing secret.
  </Step>
</Steps>

## Register your endpoint

You can configure webhooks in the [Admin Console](https://app.deepidv.com) under **Integrations > Webhooks**.

When creating a webhook, you'll provide:

| Field | Required | Description |
|-------|----------|-------------|
| Name | Yes | A label to identify this webhook |
| Destination URL | Yes | The HTTPS endpoint where events will be sent. Must be publicly accessible |
| Events | Yes | One or more event types to subscribe to |
| Description | No | Optional description for your reference |

After creating a webhook, deepidv generates a **signing secret** (prefixed with `whsec_`). Store this secret securely — you'll use it to verify that incoming webhook requests are from deepidv.

<Warning>
Your signing secret is shown once after you create or reset it. If you lose it, reset it in the webhook settings. Resetting invalidates the previous secret.
</Warning>

## Event types

deepidv sends the following event types:

| Event | Description |
|-------|-------------|
| `session.created` | A new verification session has been created |
| `session.status.submitted` | An applicant has completed and submitted their verification session |
| `session.status.verified` | A verification session has been marked as verified |
| `session.status.rejected` | A verification session has been marked as rejected |
| `session.status.expired` | A verification session has expired |
| `session.status.failed` | A verification session has hit the configured failed-attempt limit and been auto-failed |

You can subscribe to all events or only the ones relevant to your integration. See the [Event Object](/webhooks/event-object) reference for the full payload structure.

## Create a handler

Set up an HTTPS endpoint that accepts POST requests with a JSON body.

1. Read the raw request body and [verify the signature](#verifying-webhooks).
2. Parse the JSON into an [event object](/webhooks/event-object). Use the event's top-level `id` to identify duplicate deliveries.
3. Queue new events for processing and respond with a `2xx` status within 10 seconds.

## Verifying webhooks

Every delivery includes a `deepidv-webhook-signature` header in the format `t=<timestamp>,v1=<digest>`. The timestamp is Unix time in seconds. The digest is the hexadecimal HMAC-SHA256 of the timestamp, a period, and the raw request body. Use the full signing secret, including the `whsec_` prefix, as the HMAC key.

Verify the raw body before parsing JSON. Reject the request if the signature is missing, invalid, or the timestamp differs from your server's current time by more than five minutes. A header can contain multiple `v1` values to support future secret rotation. Accept the delivery if any `v1` value matches the computed digest in constant time.

In Express, use `express.raw({ type: "application/json" })` on the webhook route before JSON parsing. In Flask, pass the bytes from `request.get_data()` and the header from `request.headers.get("deepidv-webhook-signature")` to the verifier before calling `request.get_json()`.

<CodeGroup>

```javascript Node.js
import crypto from "node:crypto";

export function verifyDeepidvWebhook(rawBody, signatureHeader, secret, toleranceSeconds = 300) {
  if (!signatureHeader) return false;
  let timestamp = null;
  const signatures = [];
  for (const part of signatureHeader.split(",")) {
    const [key, value] = part.trim().split("=");
    if (key === "t") timestamp = Number(value);
    if (key === "v1" && value) signatures.push(value);
  }
  if (!Number.isInteger(timestamp) || signatures.length === 0) return false;
  if (Math.abs(Math.floor(Date.now() / 1000) - timestamp) > toleranceSeconds) return false;

  const expected = crypto.createHmac("sha256", secret).update(`${timestamp}.${rawBody}`).digest("hex");
  const expectedBuf = Buffer.from(expected, "hex");
  return signatures.some((sig) => {
    const sigBuf = Buffer.from(sig, "hex");
    return sigBuf.length === expectedBuf.length && crypto.timingSafeEqual(sigBuf, expectedBuf);
  });
}
```

```python Python
import hashlib, hmac, time

def verify_deepidv_webhook(raw_body: bytes, signature_header: str, secret: str, tolerance_seconds: int = 300) -> bool:
    if not signature_header:
        return False
    timestamp, signatures = None, []
    for part in signature_header.split(","):
        key, _, value = part.strip().partition("=")
        if key == "t" and value.isdigit():
            timestamp = int(value)
        elif key == "v1" and value:
            signatures.append(value)
    if timestamp is None or not signatures:
        return False
    if abs(int(time.time()) - timestamp) > tolerance_seconds:
        return False
    signed = f"{timestamp}.".encode() + raw_body
    expected = hmac.new(secret.encode(), signed, hashlib.sha256).hexdigest()
    return any(hmac.compare_digest(expected, sig) for sig in signatures)
```

### Legacy `deepidv-signature` header (deprecated)

Existing endpoints that still have legacy signing enabled also receive `deepidv-signature`. That header contains the signing secret itself. Use the v1 HMAC header to verify deliveries. New endpoints use v1 signing by default and can opt into legacy signing during migration.

Update your receiver to verify `deepidv-webhook-signature`, then disable the legacy header for that endpoint in the webhook settings. After you turn it off, deepidv removes `deepidv-signature` from subsequent deliveries to that endpoint.

<Warning>
The legacy header removal deadline is `<DEADLINE: 90 days from email send>`. If a legacy signing secret may be in your logs, reset it after migrating the endpoint.
</Warning>

## Test your webhook

You can send a test event from the Admin Console to verify your endpoint is working correctly:

1. Go to **Integrations > Webhooks** in the [Admin Console](https://app.deepidv.com)
2. Select your webhook
3. Click **Send Test Event**
4. Choose the event type to test
5. Check your endpoint for the received event

The test event contains sample data that matches the structure of a real event, so you can use it to validate your handler logic.

## Retry behavior

deepidv waits up to 10 seconds for your endpoint to respond. Automatic retries target the endpoint that failed and keep the same event `id` and `created_at`.

| Scenario | Behavior |
|----------|----------|
| `2xx` response | Delivered successfully |
| `3xx` response | No automatic retry |
| `4xx` response other than `429` | No automatic retry |
| `429 Too Many Requests` | Retried with backoff, honoring `Retry-After` |
| `5xx` response, timeout, or unreachable endpoint | Retried with backoff. Timeouts are logged as HTTP 408 |

After each retryable failure, deepidv waits for the next delay in the schedule. Delays are measured from the failed attempt.

| Failed attempt | Delay before the next attempt |
|----------------|-------------------------------|
| 1 | 1 minute |
| 2 | 5 minutes |
| 3 | 30 minutes |
| 4 | 2 hours |
| 5 | 6 hours |
| 6 | 12 hours |
| 7 | 24 hours |

The standard schedule allows up to eight total attempts over about 45 hours. On a `429` response, `Retry-After` can be a number of seconds or an HTTP date. The next attempt waits for the longer of the scheduled delay and `Retry-After`, capped at 24 hours. A missing or invalid `Retry-After` uses the standard delay.

## Best practices

### Return a 200 response quickly

Your endpoint should return a `200` response before performing any complex logic. Defer processing to a background job or queue to avoid timeouts.

### Handle duplicate events

Deduplicate deliveries using the top-level event `id`. Deliveries can arrive out of order. Use the event's `created_at` for event time.

### Only listen to events you need

Subscribe only to the event types your integration requires. This reduces unnecessary load on your server.

### Process events asynchronously

Use an asynchronous queue to process incoming events. This prevents large spikes in webhook deliveries from overwhelming your server.

### Use HTTPS

Your webhook endpoint must use HTTPS to receive events. deepidv will not send events to HTTP endpoints.

### Keep your signing secret secure

Store your signing secret in an environment variable or secret manager — never hardcode it in your application. If you suspect your secret has been compromised, reset it immediately from the Admin Console.
